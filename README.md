# AGNIYA

Encrypted aggregation for tabular data: SUM / AVG / COUNT (and OPE range filters) computed on
**Paillier-2048** ciphertexts, with a Flask API and a Next.js dashboard.

**System architecture:** [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) (components, key custody, data model, API,
query flows, leakage, measured performance, and the path to a bank deployment).

```python
import agniya as ag

db = ag.Database()                    # 2048-bit Paillier key pair
cts = db.encrypt([100, 200, 300])     # randomized: same value -> different ciphertexts
db.sum(cts, encrypted=True)           # 600, computed by multiplying ciphertexts

col = db.encrypt_column(list(range(1, 20_001)))   # packed: ~60-200 values per ciphertext
db.sum_column(col)                    # 200010000, one ciphertext product + one decryption
```

With the keys kept by the data owner and an untrusted server (`/api/v2`):

```python
from agniya.client import AgniyaClient

c = AgniyaClient("http://127.0.0.1:5000", dataset="claims")    # private key + OPE keys stay here
c.upload("charges", charges, decimals=4, range_filter=True)      # server gets ciphertexts + OPE tags
c.query("charges")                    # {'sum', 'count', 'avg'}: server multiplies, client decrypts and checks
c.query("charges", lo=5000, hi=20000)
c.upload_by("charges", charges, by="age", by_values=ages, decimals=4)  # charges packed in age order
c.query("charges", lo=30, hi=45, by="age")                       # SUM(charges) WHERE 30 <= age <= 45
c.upload_grouped("charges", charges, by="region", by_values=regions, decimals=4)
c.query_groups("charges", "region")   # {label: {'sum', 'count', 'avg'}} for every region, one decryption
c.quantiles("charges", [0, 0.5, 1], lo=5000, hi=20000)          # MIN, MEDIAN, MAX (range_filter=True columns)
c.upload_sorted_groups("charges", charges, by="region", by_values=regions, decimals=4)
c.quantiles("charges", [0, 0.5, 1], by="region")                # {'northeast': [MIN, MEDIAN, MAX], ...}
c.upload_sorted_groups("charges", charges, by="region", by_values=regions, decimals=4, where="age", where_values=ages)
c.quantiles("charges", [0.5], lo=30, hi=45, by="region", where="age")  # MEDIAN ... WHERE 30 <= age <= 45 GROUP BY region
c.upload("charges", charges, decimals=4, range_filter=True, squares=True)
c.query("charges", lo=5000, hi=20000)  # ... plus 'var' and 'std' (VARIANCE / STDDEV, ddof=1 as pandas)
c.save("claims.agniya-key", password)                            # all client secrets, encrypted
c = AgniyaClient.load("claims.agniya-key", password, "http://127.0.0.1:5000")
```

## Banking demo

`data/bank_customers.csv` holds 2,000 synthetic bank customers (generated by `tools/make_bank_data.py`; no real
data). Load it in the dashboard, set `credit_score` to Paillier + range (OPE+Paillier), encrypt, and step 3 offers six
one-click banking use cases (loan exposure by risk band, default rate by segment, median balance by region,
spend volatility, sub-prime exposure by product, exposure by region and segment), each an ordinary encrypted
query. How this would be deployed at a bank, what is missing for production, and a pilot plan:

Lattice FHE (SEAL) still encrypts bulk data faster per value; Paillier's strengths are exact integer sums,
small per-value ciphertexts and simplicity. The plan for closing the gap is in
[docs/PROJECT_REVIEW.md §9](docs/PROJECT_REVIEW.md).

## How it works

- **Paillier** with `g = n+1`, fresh randomness `r` for every ciphertext, CRT decryption (`agniya/core/paillier.py`).
- **Randomness pool**: the expensive `rⁿ mod n²` is plaintext-independent, so it is precomputed offline across all cores; each value is used once (`agniya/core/precomputation.py`).
- **Fast rⁿ (DJN)**: by default rⁿ is computed as `hsᵅ` for a fixed public base `hs = hⁿ` (`h = −x² mod n`) and a random ⌈|n|/2⌉-bit `α`, using a precomputed comb table (`agniya/core/djn.py`). This is the Damgård–Jurik–Nielsen construction (2010, §4.1). On an admissible modulus it is as secure as textbook Paillier under DCR, so key generation uses safe primes `p ≡ q ≡ 3 (mod 4)`; keys that are not admissible (e.g. made in the browser) automatically use textbook randomness. `AGNIYA_RN_METHOD=standard` forces textbook randomness.
- **Packing**: many integers per plaintext in fixed slots, sized with enough headroom that slot sums cannot overflow; negatives via a public offset (`agniya/core/batch_packing.py`).
- **OPE + Paillier** for range filters: the column is packed in sorted order and each row gets an order-preserving tag, so a range is a contiguous run of slots: whole ciphertexts are multiplied, the two edge ciphertexts are decrypted separately (`api/server_optimized.py`, `BatchedAggregator.sum_range`). Tags come from `agniya/hybrid/fast_ope.py`: pyope's scheme with bit-identical tags, computed once per distinct value over one shared tree walk.
- **AES-256-GCM** for non-numeric columns (`agniya/hybrid/aes_cipher.py`).

## Security model and limitations (read this)

- **Two modes.** The server-side endpoints (`/api/upload`, `/api/encrypt`, `/api/query`; the dashboard's "Who holds the key? The server" choice) receive the plaintext CSV, and the server generates and holds the private key in memory: there the server **is the data owner**. The `/api/v2` endpoints keep the private key, the OPE keys and all plaintext on the client: either `agniya.client.AgniyaClient` (Python) or the dashboard's default **"Who holds the key? This browser"** mode (`webapp/lib/agniya-browser.ts`: Paillier, packing and a port of pyope in TypeScript, cross-checked against Python by `tests/test_integration/test_browser_crypto.py`). In browser mode the crypto runs in a Web Worker (`webapp/lib/agniya-worker.ts`), so the page stays responsive and the key lives only in that worker (big encryption batches are split across helper workers, one per spare core up to 8, which get the key from it and end with it: `webapp/lib/agniya-encrypt-worker.ts`; on the insurance CSV the first GROUP BY age WHERE age in a range, which builds a 47-group copy, went from 22.1 s to 6.2 s): after encrypting you can download a password-protected key file and restore it later ("Reopen a saved session"). The format is the same as `AgniyaClient.save`, so the Python client and the browser can each open the other's file. Without that file, closing the tab makes the uploaded data undecryptable. the server stores and sees only the public modulus `n`, packed ciphertexts, values per ciphertext, row counts and sorted OPE tags, and answers with ciphertexts (`range_plan` needs only the public key).
- **Integrity (client-held keys).** The `/api/v2` client checks every answer, so a server that computes wrongly is caught, not only one that looks at data (`agniya/core/integrity.py`, mirrored in the browser). Each packed plaintext carries a tag `(alpha * m + beta(c)) mod 2^127-1` in 159 bits above its data, under a fresh per-column key the server never sees (alpha and the betas are AES-256-CTR keystream). Products add tags like data, so a product that is not exactly the stored ciphertexts the query needs (an extra, missing or doubled ciphertext, an added constant, another page's answer) fails the check with probability about 1 - 2^-127. For range filters the client also stores a MAC of each ciphertext's OPE tags; the server returns the tags around both ends of the range with their MACs, which shows the range was cut at the right rows. Failures raise `IntegrityError` (Python) or "Integrity check failed" (browser), malformed answers included. Update the server before the clients: a server from before integrity tags sends no rows or witnesses, so range queries on new columns fail the check. Cost: the 159 reserved bits are about 8% of a 2048-bit plaintext, so a column takes up to that many more ciphertexts (or a different GROUP BY layout: GROUP BY age needs 3 pages instead of 4 with client-held keys). Checking an answer adds 0.03 ms (SUM) to 0.4 ms (range SUM, GROUP BY age) on insurance_real.csv, measured against the same queries with the checks skipped. An older upload of the same column is also caught (each upload gets a new key). Not covered: a server can still refuse to answer, and columns from key files made before integrity tags are not checked.
- `AgniyaClient.save` writes the Paillier primes, OPE keys and column layouts to one file, encrypted with AES-256-GCM under a scrypt key (N=2¹⁷, r=8, p=1, 128 MiB) derived from a password. The file header is authenticated. A wrong password or any modification fails to load. **Losing the file or the password makes the data undecryptable.** The password is the weakest link: use a long one. The `/api/v2` server stores its columns (ciphertexts, slots, counts, OPE tags, `n`) in SQLite at `AGNIYA_STORE` (default `api/agniya_store.sqlite3`, git-ignored) and reloads them at start-up. The dashboard endpoints stay in memory on purpose, because they hold the private key.
- Paillier is IND-CPA secure under DCR. That includes the default DJN randomness: DJN 2010 §4.1 shows short-exponent `hᵅ` is indistinguishable from uniform assuming factoring is hard (implied by DCR), for admissible moduli, which `generate_keypair` produces (safe primes, ~2–6 s for 2048-bit keys). Neither is **post-quantum**. 2048-bit keys give ~112-bit security; 3072-bit (~128-bit) costs ~1.9× per value end to end (see `docs/PROJECT_REVIEW.md` §0f).
- Packed ciphertexts reveal the number of rows. The fixed-point scale and the column offset are public.
- **OPE tags leak the order of values** and more (Boldyreva et al. 2011; Naveed et al., CCS 2015). Use `OPE+Paillier` only for columns where that is acceptable. Sorted packing reveals nothing beyond that order. For a range SUM the key holder decrypts the (at most two) ciphertexts cut by the range edges on their own, so it sees those slots' values individually.
- **`SUM(a) WHERE b in range`** works by storing a second packed copy of `a` in `b`'s sorted order, with `b`'s OPE tags (`AgniyaClient.upload_by`, `BrowserClient.uploadBy` in the browser; `/api/encrypt` builds one per pair of an OPE+Paillier column and another encrypted column; the dashboard's browser mode builds each copy, and each GROUP BY copy, the first time a query needs it, so encryption covers only the columns themselves; the dashboard's "Range filter on" picker queries them). The server learns `b`'s order, as for any OPE column, plus which ciphertext slots line up with it; each copy costs as much storage and encryption time as the column itself. Rows where `a` or `b` is missing are left out, as in SQL.
- **`SUM / COUNT / AVG(a) GROUP BY g`** packs `a` by group: in every ciphertext each group owns a block of slots (several value lanes plus one count slot), so multiplying all ciphertexts sums each group in its own slots and **one decryption returns every group's sum and count**. The labels and group sizes stay with the key holder; the server sees the slot count and the number of ciphertexts (roughly the biggest group's size divided by the lanes). When the groups do not all fit one plaintext (at 2048 bits, about 26 groups of 500 rows with 30-bit values such as fixed-point charges), they are split into pages: each page is its own run of ciphertexts, multiplied and decrypted on its own, and every page has the same number of ciphertexts so the server learns only the number of pages, not more group sizes. The layout keeps one page whenever possible; otherwise it picks the fewest ciphertexts, counting each extra decryption per query as 16 ciphertexts. GROUP BY age on insurance_real.csv (47 groups) takes 4 pages and 14 ms server-side. With client-held keys each page is its own server column (`charges#age`, `charges#age@1`, ...). `/api/encrypt` and the dashboard's browser mode build a copy per encrypted column and per column with 2–64 distinct values, which raises the ciphertext count (insurance_real.csv: 24 → 256), and the dashboard's "Group by" picker queries them. Rows missing `a` or `g` are left out, as in pandas `groupby`. **With a range filter** (`... WHERE lo <= w <= hi GROUP BY g`), a second layout packs the rows in `w` order instead: row r goes to ciphertext r / lanes, lane r % lanes of its group's block, holding value + 1 (so 0 marks a lane of another group). A range of `w` is then a run of ciphertexts, cut by OPE tags exactly like a plain range filter: the whole ciphertexts are multiplied and decrypted once, and the at most two edge ciphertexts are decrypted on their own. This copy takes about rows / lanes ciphertexts per page (more than the plain GROUP BY copy: every row takes a lane in every page; age with a bmi range takes 8 pages and 31 ms) and the server learns what any range filter shows (the order of `w` and the row count in range). `upload_grouped(..., where=, where_values=)` / `query_groups(..., lo, hi, where=)` and `BrowserClient.uploadGrouped` / `queryGroups` build and query it. The dashboard builds it on the first grouped query with a range, in both modes, since one copy per field, group and filter column up front would multiply the ciphertexts.
- **`GROUP BY` several columns**, e.g. `GROUP BY region, smoker`, for every grouped query above and below (SUM / COUNT / AVG, VARIANCE / STDDEV, MIN / MAX / MEDIAN, with or without a range). Each row's label is the combination of its values: `by=["region", "smoker"]` with `by_values=[regions, smokers]` in the Python client (tuple labels, as pandas), a label "southeast, yes" in the browser and server-side mode (`group_by: "region,smoker"`; the dashboard's "Then by" picker). Rows missing any part drop out, as in pandas. The copy is built on first use; up to 64 combinations, as for one column. Leakage is that of a one-column GROUP BY with that many groups.
- **`MIN / MAX / MEDIAN` and any quantile** of an `OPE+Paillier` column, optionally with a range on it (`AgniyaClient.quantiles`, `BrowserClient.quantiles`, `/api/v2/quantiles`; `/api/query` types `MIN`, `MAX`, `MEDIAN`; the dashboard's operation picker). The column is already packed in sorted order, so quantile q of rows i..j-1 is row i + q·(j−i−1): the server returns the one ciphertext holding it (two when pandas' linear interpolation falls between rows), and the key holder decrypts it and reads one slot. Results match pandas `quantile` exactly. The answer is checked like a SUM: the integrity tag of each ciphertext, and the range cut through the OPE-tag witnesses. Leakage: the server learns which sorted positions were asked for (it already knows the order), and the key holder sees the other values in the decrypted ciphertext, as for a range edge.
- **`MIN / MAX / MEDIAN` and any quantile per group** (`AgniyaClient.upload_sorted_groups` + `quantiles(..., by=)`, `BrowserClient.uploadSortedGroups` + `groupQuantiles`; `/api/query` `MIN`, `MAX`, `MEDIAN` with `group_by`, optionally with a range; the dashboard's operation picker with a GROUP BY). Any Paillier field works, not only OPE ones: a copy `column#by^sorted` holds the column sorted within each group, group after group. The labels and group sizes stay with the client, which works out each group's quantile rows and asks `/api/v2/ciphertexts` for the ciphertexts holding them by index; each is checked against its integrity tag before its slot is read. Results match pandas `groupby(...).quantile`. The dashboard builds the copy on first use. Leakage: the server sees which ciphertexts were read, so roughly where each group starts and ends (to within one ciphertext of rows); the key holder sees the other values in those ciphertexts. **With a range** (`where=` / `where`, e.g. `MEDIAN(charges) WHERE age BETWEEN 30 AND 45 GROUP BY region`), the copy `column#by^sorted|where` is sorted by (group, where, value) and carries OPE tags of group·span + where, so one tag pair per group selects that group's rows in range; `/api/v2/ranges` returns each group's row range with the witnesses, and the client checks every cut as for a SUM. When the range is on the column itself the rows in range are already sorted, so only the quantile rows are read; on another column every row in range is read and sorted on the client (one decryption per ciphertext of them). Extra leakage: the tags show the order of the where values within each group and, by the jumps between groups, where each group starts.
- **`VARIANCE / STDDEV`** (sample, ddof=1, as pandas and SQL), with ranges, `by=` filters and `GROUP BY` (`squares=True` on `upload`, `upload_by` and `upload_grouped` and their browser twins; `/api/query` types `VARIANCE`, `STDDEV`; the dashboard's operation picker). A copy `name^2` holds (x − c)² for every row, with c (about the mean) kept by the client, packed in the same order and, for sorted copies, with the same OPE tags, so one range cuts both. `query` and `query_groups` then also return `var` and `std`: var = (n·Σ(x−c)² − (Σx − n·c)²) / (n(n−1)), computed exactly from the two decrypted sums. Both sums are checked like any SUM, and their row counts must match. The dashboard builds the copy on first use (server-side mode too); after a key-file restore it needs the CSV unless the copy was uploaded before. Cost: a second upload of each copy, with roughly twice the bits per value. Leakage: the server sees the copy's ciphertext count, which shows roughly how wide the values' spread is.
- **Dataset tokens (`/api/v2`).** Every call (upload, aggregate, quantiles, delete) carries the dataset's token, `SHA-256("agniya/v2 dataset token" ‖ min(p, q) ‖ dataset)`: only the private key's holder can compute it, so key files need nothing new, and the Python client and the browser compute the same one. The server stores only its SHA-256 (table `owners`); a missing token is 401, a wrong one 403. Without it, anyone who learned a dataset's public `n` could overwrite or delete it, and anyone could query its ciphertexts and OPE tags. A dataset stored before tokens existed is claimed by the first token sent for it. There is no rate limiting, and the server-side demo endpoints (`/api/upload`, `/api/encrypt`, `/api/query`) have no authentication; the API binds to `127.0.0.1` by default.

## Setup

Requires Python 3.12 (wheels for gmpy2/numba) and Node.js 18+ (22.18+ to run the TypeScript cross-check tests).

```powershell
py -3.12 -m venv envb
.\envb\Scripts\Activate.ps1
pip install -r requirements.txt
pip install -e .
cd webapp; npm install; cd ..
```

Run:

```powershell
.\start.ps1                                  # API on 127.0.0.1:5000 + dashboard on localhost:3000
python -m pytest tests                       # unit tests
python -X utf8 tools\bench.py                # benchmarks (writes tools/bench_results.json)
```

API server options (environment variables): `AGNIYA_STORE` (SQLite file for `/api/v2` columns), `AGNIYA_HOST` (default `127.0.0.1`),
`AGNIYA_DEBUG=1` (Werkzeug debugger; never on a network), `AGNIYA_CORS_ORIGINS`
(default `http://localhost:3000`).

## History

Before the `phase0-honest-baseline` cleanup, this README advertised figures such as
"6.7M ops/sec", "1000×/74,426× caching" and "6,034× faster than SEAL". They came from a
deterministic plaintext→ciphertext cache (which broke Paillier's security), hard-coded benchmark
stubs, and GPU/JIT paths that could not run with 2048-bit integers. The audit and the measurements
are in [docs/PROJECT_REVIEW.md](docs/PROJECT_REVIEW.md).
